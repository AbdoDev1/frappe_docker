# biozone-discovery — بوابة الفحص قبل أي تعديل

## 0) طبيعة هذه الـskill (حد ملزم)

- هذه الـskill **تتحقق وتقترح وتعرض الأدلة فقط**.
- **ممنوع عليها**: أي تعديل ملف (إنشاء/تحرير/حذف)، أي `commit`، أي `push`، أي تنفيذ أمر تشغيلي أو إنتاجي.
- **الأوامر التشغيلية — بما فيها `bench execute` — تُعرض نصًا فقط** بترتيبها وآثارها، **ولا تُنفذ إلا بعد موافقة صريحة منفصلة** من المالك.
- مخالفة هذا = فشل المهمة حتى لو كان التشخيص صحيحًا.

## 1) متى تُستدعى / متى لا تُستدعى

**تُستدعى قبل:**
- أي تعديل كود أو قالب أو إعداد.
- أي تحليل عطل متعلق بالكود.
- أي قرار قد يؤدي إلى تعديل أو إلى أمر تشغيلي (بناء/recreate/migrate/restore/bench).

**لا تُستدعى** للشرح النظري العام أو المقارنة النظرية بين خيارين ما لم تفضِ إلى تعديل أو أمر تشغيلي.

## 2) قاعدة عدم التخمين (ملزمة — §2.4.2/3)

- صنّف كل ادعاء حسب مصدره:
  - مثبت بالفحص الحالي.
  - مقدم من المستخدم ولم يُتحقق منه.
  - مستنتج، مع وسمه بوضوح.
  - غير معروف.
- لا تقدّم معلومة قدمها المستخدم كأنها نتيجة فحص حالي.
- الغموض لا يُفسَّر ولا يُخمَّن ولا يُملأ بالافتراضات.
- إذا اتضح أثناء الفحص أن المشكلة أكبر أو أصغر من الوصف:
  أوقف الفحص وأعد وصف الحالة.
- أي نقطة لم تُفحص تُسجل في «نقاط الغموض».

## 3) قاعدة diff الحرفي (ملزمة — القاعدة 4)

- أي diff يُعرض يجب أن يكون ناتجًا حرفيًا من `git diff`
  أو `git diff --cached` أو diff على ملفات مقروءة فعليًا.
- `git status --short` يثبت حالة الشجرة فقط، وليس diff.
- افحص عند الحاجة:
  - `git status --short`
  - `git diff`
  - `git diff --cached`
- إذا لم يوجد diff حالي، اعرض صراحة: «لا يوجد diff».
- لا تنشئ diff وهميًا.
- أي diff مقترح وغير منفذ يجب وسمه:
  «مقترح — غير منفذ»، وفصله عن diff الحالي.

## 4) قاعدة منع الحقن المخفي في الاختبار (§6.7/P5)

- أي حقن في سياق اختبار (مثال: حقن `csrf_token` يدويًا) يتطلب تبريرًا مكتوبًا — أو يُعد إخفاءً للعيب.
- تصيير أي صفحة تحوي `tojson` يُختبر **بلا حقن** (ظروف الإنتاج).

## 5) خطوات الفحص (قراءة فقط)

1. اقرأ الكود فعليًا (لا تخمين): الملفات المعنية `file:line` + السياق المحيط.
2. استخدم أدوات القراءة والبحث المتاحة، مثل:
   read / glob / grep / git status / git diff / git log.
   لا يُعد الأمر آمنًا لمجرد أنه read-only؛ فإذا اتصل ببيئة
   حية أو قرأ إنتاجًا أو نفذ `bench` أو `restore` أو `migrate`
   فيُعرض نصه فقط وينتظر موافقة منفصلة.
3. ثبّت الحالة الحالية كما هي في السيستم الآن — لا كما يفترضها أحد.
4. حدد الأثر: ما الذي ينكسر أو تأثر فعليًا.
5. اعرض الخيارات والحلول **دون توصية تنفيذية** ودون بدء تنفيذ.

## 6) مخرج التقرير الثابت (إلزامي — ثم STOP)

```text
1. الحالة الحالية المثبتة
2. الأدلة: file:line ونتائج الأوامر
3. diff الحالي، أو "لا يوجد diff"
4. المشكلة
5. الأثر وما قد ينكسر
6. الخيارات دون توصية تنفيذية
7. نقاط الغموض
   مصادر الفحص:
   - الأوامر التي شُغّلت:
   - الملفات المقروءة:
   - commit أو SHA الحالي:
   - حدود الفحص:
8. STOP — بانتظار أمر صريح منفصل قبل أي تعديل
```

  ولا تحسمه تلقائيًا.
- الـskills العامة مرجع تشخيص لنمط Frappe v16،
  وليست مصدرًا لأوامر إنتاجية.

  `AGENTS.md` أو موافقة المالك.
- `commit` لا يعني إغلاق المهمة؛ تحديث الخطة يتم في Prompt
  منفصل بعد أي commit مأذون.
